# CLAUDE.md - snow-crystal-sim（雪の結晶シミュレータ）

Claude Code に対するこのシミュレータ固有の指示。Codex 向けの指示は同ディレクトリの
`AGENTS.md`、リポジトリ共通の方針はルートの `CLAUDE.md` を参照する。

## 概要

温度と過飽和度による雪の結晶の形態変化（中谷ダイヤグラム）を可視化するシミュレータ。
中谷ダイヤグラム上のマーカーをドラッグする操作が、**結晶が雲の中を落下する軌跡を描く**
ことに対応し、その履歴が結晶の形として残る。

**現在の状態**: 計画のみ。`apps/snow-crystal-sim/` にはまだ workspace が存在しない
（`package.json` 等は `TASKS.md` の T0-2 で作成する）。それまで下記の検証コマンドは動かない。

## このアプリで特に注意すべき3点

### 1. 形態写像は「経験的な較正」である

`(温度, 過飽和度)` から成長パラメータへの対応付けは、観測される形態領域に合わせた
**経験的な較正**であり、第一原理からの導出ではない。中谷ダイヤグラムの板／柱の交替は
約50年にわたり未解明の研究課題であり、最先端の3次元モデルでさえ自由パラメータは緩くしか
拘束されていない（`SPEC.md`「成長コア」節）。**較正であることを、コード・UI・説明の
いずれにおいても隠してはならない。**

### 2. 六回対称性は「強制」せず「創発」させる

6本の腕は同じ環境を共有するため歩調が揃うが、互いに情報をやりとりしないため完全対称には
ならない。これが実物の物理である。したがって:

- **60° セクターだけを計算してミラー・回転で複製してはならない。** 格子全体を計算する
- 対称性は、6本の腕が同じ (T, σ) の履歴を受けた結果として現れさせる
- AC-05 がこれをテストで縛っている

### 3. 主題は結晶形態である

結晶の形は成長計算の結果として現れさせる。あらかじめ用意した六角形や樹枝のテクスチャ・
曲線で描いてはならない。一方、**主題でない部分（雲の鉛直構造、着氷、融解）は `SPEC.md` で
明示的に対象外としてある**。対象外を勝手に実装しない。

## 層の境界

```text
src/simulators/snow-crystal-sim/
  domain/   六角格子の成長計算と形態パラメータ（Three.js・DOM 非依存の純粋関数）
  app/      軌跡の記録、履歴管理、共有 URL、表示用データ変換
  ui/       中谷ダイヤグラム操作盤、タイムライン、情報バー、ヘルプ
  scene/    Three.js による立体化と描画
```

- `domain/` は `three` を import してはならず、`document` / `window` / `navigator` などの
  ブラウザグローバルにも触れてはならない。**`scripts/check-architecture.mjs` が機械的に
  検出して失敗させる**
- `domain/` は副作用のない純粋関数のみで構成する。同一入力に必ず同一出力を返す
- `ui/` と `scene/` は `domain/` の公開 API だけを使い、内部表現に依存しない
- 成長計算のタスクと UI・統合のタスクを1つにまとめない

## 規約

### 命名と単位

- 温度は °C、過飽和度は `SPEC.md` が定める量。**単位を変数名に明示する**（`temperatureC` 等）
- 角度は内部でラジアン、UI 境界のみ度。変数名に `Rad` / `Deg` を付す（`angle` は禁止）
- 六角格子は軸座標（axial coordinates）で保持し、`q` / `r` と直交座標を混同しない
- ファイル名: クラスを default export するものは PascalCase、関数群は camelCase
- 定数は UPPER_SNAKE_CASE
- 公開関数には日本語の JSDoc を付け、**引数の単位**と**戻り値の意味**を書く

### フォーマット

インデント 2 スペース、行長 100 文字、セミコロン必須、シングルクォート、
import は外部ライブラリ → 自作モジュールの順（間に空行）。

### TypeScript

- `any` は禁止。不明な入力は `unknown` で受けて絞り込む
- `strict: true`

### Three.js 運用

- **描画ホットパスで毎フレーム `new` しない。** 適用範囲は `scene/` とレンダーループ内
- `domain/` は純粋性を優先する。割り当てが性能に響くかは T5-1（性能実測）で測り、
  **問題が出た場合にのみ**高速経路を追加する
- ジオメトリ・マテリアルは `dispose()` 可能な形で保持する
- **結晶の描画は六角柱ジオメトリ1つの `InstancedMesh`** とし、セルごとの厚みと氷の濃度を
  インスタンス属性バッファへ書き込んで `needsUpdate` を立てる。毎フレームのジオメトリ
  再生成は禁止
- **成長ステップと描画フレームを分離する。** 成長は 10〜20 回/秒に間引き、描画は 60 fps を
  維持する。成長していないフレームでインスタンス属性を書き換えない

### コメント

- 日本語で書く。物理・数値の根拠を1行添える
- 自明なコードにコメントを書かない

## テスト方針

| 環境 | 対象 |
|---|---|
| Vitest `node`（既定） | `domain/` 全体、`app/` の状態ロジック |
| Vitest `jsdom` | DOM 構造と UI ⇄ 状態の束縛、a11y の意味論（`role` / 名前 / `legend`） |
| ブラウザでの受入確認 | 実描画、fps、結晶の見た目 |

- jsdom を使うファイルは**先頭に `// @vitest-environment jsdom` を書く**。全体を jsdom に
  しない
- **jsdom で見た目・寸法・画素・WebGL を確かめようとしない。** `getBoundingClientRect` は
  0 を返す
- `domain/` は**先にテストを書いてから実装する**
- 期待値を実装と同じ経路で生成しない。独立オラクル（水蒸気の収支、成長コードとは別に
  実装する形態指標関数、腕の分散の統計、決定性）は `DESIGN-OUTLINE.md`「物理・数値の決定」に
  定めてある

## やってはいけないこと

- ❌ `domain/` から `three`・DOM・シーングラフに触れること
- ❌ **60° セクターを計算してミラー・回転で複製すること**（実在しない完全対称を作る。上記2）
- ❌ **結晶の形を、用意した曲線・テクスチャ・図形で描くこと。** 成長計算の結果として現れさせる
- ❌ **形態写像を「物理から導出した」かのように説明すること。** 経験的較正である（上記1）
- ❌ 出典のない数値をコードへ書くこと。`SPEC.md`「出典」節から取り、出典コメントを付ける。
  値を変えるときは `SPEC.md` を先に更新する
- ❌ `domain/` でグローバルな `Math.random` を呼ぶこと（seed を引数で受け取る。AC-06 の再現性）
- ❌ 毎フレームのジオメトリ再生成
- ❌ 結晶が格子外縁に達したときに、無音で格子を拡張すること（UI に通知する）
- ❌ CDN からの実行時スクリプト読み込み（依存は npm で固定する）
- ❌ 他の `apps/*` のコードを import すること
- ❌ `SPEC.md` からの逸脱を独断で行うこと

## 進め方

1. **`TASKS.md` のタスク単位で進める。** 着手時に対象タスクの実行プロファイル・UI影響・
   依存・変更境界を確認する
2. 完了時は `TASKS.md` の当該タスクの「状態」を更新して報告する
3. 次に該当する場合は独断で進めず確認する
   - 仕様、受入基準、優先順位、画面デザインの変更
   - 成長則・形態写像・較正値など、振る舞いを変える物理的判断
   - `DESIGN-OUTLINE.md` の未決定事項の決着
4. Git のコミットは人間の明示承認を得てから行う。`git add .` / `git add -A` を使わず、
   対象パスだけをステージする
