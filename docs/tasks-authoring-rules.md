# TASKS.md 作成ルール

## 目的

`TASKS.md` は、シミュレータを小さく安全に開発するための実行計画である。Codex への実行指示、担当エージェントの割り当て、進捗の確認に使用する。設計書や実装の詳細を重複して記載する場所ではない。

このルールは、各シミュレータの `docs/simulators/<id>/TASKS.md` を新規作成・更新するときに必ず参照する。

## 基本構造

```text
シミュレータ
└─ フェーズ: 利用者価値または技術リスクを一つ減らす到達点
   └─ タスク: 選択した実行プロファイルの工程を一周できる最小の変更単位
```

- フェーズは工程名で分けない。`設計フェーズ`、`実装フェーズ`、`テストフェーズ` のような分け方は禁止する。
- プロダクトの振る舞いを変更するタスクは、③設計から⑨R実装差分レビューまでを一周して完了する。UI に影響する場合は⑩人間確認も実施する。
- 振る舞いを変更しない文書・設定・定型配線は `lightweight` を使用できるが、省略工程と理由、代替検証、差分レビューを必ず記録する。
- 一つのタスクは、原則として一つの明確な振る舞い、公開 API、または検証可能な変更を扱う。
- 物理計算と UI・統合を同じタスクに混在させない。物理 API を先に確定・実装し、UI・統合は後続タスクにする。
- フェーズ完了は、配下の全タスクが完了し、フェーズの受入条件を満たした時だけとする。

## 実行プロファイル

各タスクには、次のいずれかのプロファイルを必ず指定する。

| プロファイル | 使用条件 | 必須工程 |
|---|---|---|
| `full` | 物理計算、公開 API、ユーザーに見える振る舞いを変更する | ②P、③〜⑨R。UI 影響があれば⑩も実施 |
| `ui` | UI、操作、画面遷移、アクセシビリティを変更する | ②P、③〜⑨R、⑩ |
| `lightweight` | 振る舞いを変えない文書、設定、定型配線 | 変更方針、対象検証、差分レビュー、最終コミット |
| `emergency` | 人間が緊急対応と明示した変更 | 人間が承認した工程、最低限の検証、事後補完タスク |

`lightweight` でテストを追加しない場合は、テスト不要の理由と代替検証を記載し、Reviewer の承認を得る。プロファイルを判断できない場合や、工程省略が振る舞いへ影響する場合は人間に確認する。

## フェーズの作り方

フェーズは、ユーザーにとって確認可能な価値、または後工程の不確実性を大きく下げる技術的到達点で定義する。各フェーズにはゴール、受入条件、対象外、依存関係を記載する。

プリズム分光シミュレータの例:

| フェーズ | ゴール | 受入条件の例 |
|---|---|---|
| P0: 開発準備 | 作業を開始できる契約を確定する | `SPEC.md`、全体設計、タスク一覧をレビュー済み |
| P1: 物理計算コア | 屈折・分散を UI 非依存で計算できる | 定義域・単位・境界値を含む自動テストが通る |
| P2: 最小シミュレーション | 入力して計算結果を確認できる | 代表的な入力で結果を表示・更新できる |
| P3: 分光表現と操作性 | 分光表現と操作・エラー処理を完成させる | アクセシビリティとエラー状態のテストが通る |
| P4: 受入・品質確認 | リリース判断できる状態にする | 全検証が通り、人間による UI 確認が完了する |

P0 はシミュレータ開始時だけの準備フェーズである。P1 以降は、実際の価値やリスクを減らす順に並べる。フェーズ数を固定せず、規模に応じて増減する。

## タスクの作り方

各タスクには次を必須項目として記載する。

```md
### T<phase>-<number>: <短い成果物名>

- 目的: 完了後に可能になること
- 完了条件: 自動確認可能な条件。必要なら人間確認も明記する
- 実行プロファイル: `full` / `ui` / `lightweight` / `emergency`
- UI影響: `あり` / `なし`
- 担当分類: タスク分類表における分類と既定担当エージェント
- 依存: 先に完了している必要があるタスク。なければ「なし」
- 変更境界: 変更してよい層・ディレクトリ、および変更してはいけない境界
- 成果物: `DESIGN.md`、`TESTCASES.md`、コード、テストなど
- 状態: `未着手` / `進行中` / `レビュー待ち` / `人間確認待ち` / `stale` / `完了` / `ブロック`
```

タスクは次の粒度を満たすように分割する。

- 完了条件を一文で判定できる。
- 変更対象と依存関係を把握できる。
- 設計・テストケース・テストコードレビュー・実装レビュー・自動検証の結果を、一つの `tasks/<task-id>/` に対応付けられる。
- 物理式、単位、近似、数値計算法を新設・変更する場合は、必ず物理計算タスクにする。
- 物理計算タスクでは、数式と定数の出典、適用範囲、近似条件、単位、許容誤差、独立した参照計算または性質テストを成果物に含める。
- UI の見た目だけの変更、画面遷移、入力制御、非物理ロジックは、物理計算タスクと分ける。

大きすぎる兆候は「複数の公開 API を同時に変える」「物理モデルと画面を同時に決める」「独立して検証できる完了条件が複数ある」である。この場合は分割する。小さすぎる兆候は「コード一行を変える」だけで、単独の振る舞いや検証を持たないことである。この場合は近接した変更とまとめる。

## 担当とモデル層

タスクの担当は `docs/agent-architecture-codex.md` のタスク分類表に従う。`TASKS.md` を作成する担当者が独自にモデルを選び直してはならない。

| タスクの主内容 | 既定担当 |
|---|---|
| 要件整理、依存関係、工程ゲート | Coordinator |
| 設計、テストケース、物理計算 | ArchitectPhysics |
| 設計・テストケース・差分の独立レビュー | Reviewer |
| 環境、テストコード、非物理ロジック、UI、検証実行 | DeliveryBuilder |

複数分類にまたがる場合はタスクを分割する。分割できない、または例外条件に該当する場合は、人間に確認してから進める。

## 人間の指示と承認

- 実行を開始する指示は原則タスク単位とする。例: 「`TASKS.md` の `P1 / T1-2` を進めてください。」
- フェーズ単位の指示は、開始時の優先順位・受入条件の合意、終了時の次フェーズへの移行判断に使う。
- 設計変更、物理モデルの変更、分類不能なタスク、重大レビュー指摘、3回の修正失敗は、人間確認へ進める。
- ④設計レビュー完了後、⑦Rテストコードレビュー・⑦V Red確認後、⑨R実装差分レビュー完了後のコミットは、別途「コミットしてください」という明示承認が必要である。UI に影響するタスクの実装コミットは⑩人間確認後に提示する。

## TASKS.md テンプレート

```md
# <シミュレータ名> タスク一覧

## 運用

- 作成・更新時は `docs/tasks-authoring-rules.md` を参照する。
- 実行指示は原則タスク単位とする。

## P1: <到達点>

- ゴール: <利用者価値または技術リスクの低減>
- 受入条件: <フェーズ完了を判定する条件>
- 対象外: <このフェーズで扱わないこと>
- 依存: <先行フェーズまたはなし>

### T1-1: <短い成果物名>

- 目的: <完了後に可能になること>
- 完了条件: <自動確認可能な条件>
- 実行プロファイル: <full / ui / lightweight / emergency>
- UI影響: <あり / なし>
- 担当分類: <分類>（<既定担当エージェント>）
- 依存: <タスクIDまたはなし>
- 変更境界: <対象層・ディレクトリ>
- 成果物: <成果物一覧>
- 状態: 未着手
```

## 更新時の確認

`TASKS.md` を更新したら、次を確認する。

1. 各フェーズが工程名ではなく到達点になっている。
2. 各タスクに適切な実行プロファイルと UI 影響が指定され、必須工程を一周できる。
3. 物理計算と UI・統合が分離されている。
4. 依存関係、担当分類、変更境界が明記されている。
5. 上位の `SPEC.md` と `DESIGN-OUTLINE.md` に矛盾していない。
6. 物理計算タスクに出典、適用範囲、単位、許容誤差、独立した検証方法が含まれている。
