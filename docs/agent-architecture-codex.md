# AIエージェント構成設計（Codex）

## 目的

Codex を用いて、複数の物理シミュレータを継続的に開発するためのエージェント構成を定義する。

対象アプリは、ホーム画面、シミュレータ一覧、各シミュレータの画面からなるフロントエンド Web アプリである。初回はプリズム分光シミュレータを実装し、将来は雪の結晶、月の軌道などを追加する。サーバーサイド追加にも耐えられるよう、物理計算、アプリケーションロジック、UI を分離する。

各シミュレータは、全体要件とインターフェースを確定した後、③設計から⑨テスト実行までを小さなタスク単位で反復する。

## 採用する構成

4役構成を採用する。

| 役割 | モデル帯 | 役割の要点 |
|---|---|---|
| Coordinator | 高性能 | タスク分類、工程制御、例外判断、人間への確認、コミット管理 |
| ArchitectPhysics | 高性能 | 設計、テストケース作成、物理計算ロジックの実装 |
| Reviewer | 高性能 | 独立した read-only レビュー |
| DeliveryBuilder | コスト重視 | 環境構築、テストコード、物理計算以外のロジック、UI 実装、検証実行 |

Coordinator はメインの Codex セッションであり、ほかの3役はカスタム・サブエージェントとして定義する。各カスタム・エージェントには、利用中の Codex 環境で選択可能な `model` と `model_reasoning_effort` を明示設定する。これらを省略すると親エージェントの設定を継承し、意図したモデル帯から外れる可能性があるため、省略を禁止する。設計書ではモデル名を固定せずモデル帯で扱い、具体的なモデル ID は `.codex/agents/*.toml` で管理する。

```text
人間
  │ 要件承認、仕様・デザイン判断、UI受け入れ、コミット承認
  ▼
Coordinator［高性能］
  ├─ ArchitectPhysics［高性能・書込み可］
  ├─ Reviewer［高性能・read-only］
  └─ DeliveryBuilder［コスト重視・書込み可］
```

## モデル選択とタスク分類

人間は、各役割に対応付ける実際のモデルと推論強度、高リスク判定の基準を決める。Coordinator は新たなモデルを独断で選ばず、以下の分類表に従って既定の担当エージェントを使う。

メインセッションでモデルを変更しても、その変更をサブエージェントのモデル変更とはみなさない。タスク開始前に Coordinator は、各カスタム・エージェントのモデル ID、推論強度、権限が現在の Codex 環境で利用可能か確認する。設定モデルを利用できない場合や推論強度が非対応の場合は、別モデルへ自動で切り替えず、人間に代替候補と影響を提示して確認する。

初期の割当方針は次のとおりとする。

| 役割 | モデル設定方針 | 推論強度の方針 |
|---|---|---|
| Coordinator | 現在利用可能な高性能モデル | 通常は中〜高。例外判断では高以上 |
| ArchitectPhysics | 現在利用可能な高性能モデル | 高以上 |
| Reviewer | 現在利用可能な高性能モデル | 高以上 |
| DeliveryBuilder | 現在利用可能なコスト重視モデル | 通常は中。完全に定型的な処理だけ低を許可 |

分類不能なタスク、複数分類にまたがるタスク、または例外条件に該当するタスクでは、Coordinator は実装を始めず人間に確認する。複数分類にまたがるタスクは、原則として小さなタスクに分割してから実行する。

| タスク分類 | 担当 | モデル帯 | 例 |
|---|---|---|---|
| 要件の整理、タスク分解、工程遷移、例外判断 | Coordinator | 高性能 | 依存関係の整理、仕様確認の依頼 |
| 設計、公開 API、型の契約、数式、単位、境界条件 | ArchitectPhysics | 高性能 | 屈折率モデル、軌道計算の設計 |
| テストケースの設計 | ArchitectPhysics | 高性能 | 既知値、性質、境界値、異常系の定義 |
| 設計・テストケース・実装差分の独立レビュー | Reviewer | 高性能 | SPEC との整合、テストの不足、スコープ逸脱 |
| 物理計算の純粋関数、数値計算、アルゴリズム | ArchitectPhysics | 高性能 | スネルの法則、数値積分、結晶成長則 |
| 環境構築、設定、定型的な配線 | DeliveryBuilder | コスト重視 | Vite 設定、ルーティング、レジストリ登録 |
| テストコードの実装と実行 | DeliveryBuilder | コスト重視 | 承認済みテストケースの Vitest 化、Red / Green 確認 |
| 物理計算以外のロジック | DeliveryBuilder | コスト重視 | 状態管理、入力検証、表示用データ変換 |
| UI、スタイル、画面遷移、アクセシビリティ実装 | DeliveryBuilder | コスト重視 | カード、操作パネル、メニュー、画面表示 |

人間への確認が必要な例外は次に限定する。

- 仕様、受け入れ基準、優先順位、画面デザインの変更
- 数式、単位、近似、数値積分法など、プロダクトの振る舞いを変える物理的判断
- タスク分類ができない、または分割しても担当を決められない場合
- Reviewer が重大な設計矛盾を検出した場合
- 規定回数の修正後もテスト失敗を解消できない場合
- コスト重視モデルの担当を高性能モデルへ切り替える必要がある場合

## エージェント定義

### Coordinator

Coordinator は、すべてのタスクの入口と工程ゲートを管理する。

- `SPEC.md`、`TASKS.md`、コーディング規約、既存の設計・レビュー成果物を確認する。
- タスク開始時に作業ツリー、ステージ済み差分、既存テストの状態を記録し、今回の変更と既存変更を区別する。
- タスク分類表に従って担当エージェントを選ぶ。
- 分類不能または例外の場合だけ、人間へ選択肢と推奨を添えて確認を求める。
- サブエージェントの結果を集約し、構造化された結果を内容を変えずにレビュー成果物と判断ログへ保存する。
- 設計、テストケース作成、物理実装は工程ごとに新しいサブエージェントを起動する。テストケース作成者と物理実装者に同一の継続スレッドを使わない。
- 各レビューも対象工程ごとに新しい Reviewer サブエージェントを起動し、作成者の未記録の推論ではなく成果物だけを入力にする。
- 同じ実装ファイルだけでなく、同じ依存関係・設定・生成物へ影響する書込みタスクも並列実行しない。書込みは原則直列とし、並列化は read-only 調査または変更範囲が完全に分離された場合だけ許可する。
- 最終検証と実装差分レビューが完了するまで、タスクを完了にしない。UI に影響するタスクでは、さらに人間の UI 受け入れを必要とする。
- コミット候補では、対象ファイルだけを `git add` し、コミットメッセージ案とステージ済みファイル一覧を人間に提示する。
- 人間がこの会話で「コミットしてください」と明示承認した後にだけ、提示済みの内容を再確認して `git commit` を実行する。

Coordinator 自身は、物理モデル、テストケース、UI の詳細設計を代行しない。担当エージェントへの割当と工程の進行に集中する。

### ArchitectPhysics

ArchitectPhysics は、高性能モデルで実行する設計・物理計算専門エージェントである。

責務。

1. タスクの設計書を作成する。
2. 入出力、型、単位、境界条件、エラー、物理的根拠を設計書に記録する。
3. 物理計算と数値計算のテストケースを作成する。UI タスクでも、受け入れ条件と状態遷移のテストケースを定義する。
4. 承認済みのテストケースを前提に、物理計算ロジックだけを実装する。
5. 物理計算の疑問を、仕様と既存資料で解消できるか確認する。解消できず振る舞いを左右する場合は Coordinator へ停止を報告する。

物理計算の設計とテストケースには、数式と定数の出典、適用可能範囲、近似条件、単位、数値許容誤差の根拠、乱数を使う場合の seed と再現条件を記載する。既知値、次元解析、性質テスト、独立した参照計算を組み合わせ、実装対象と同じ関数または同じ計算経路だけで期待値を生成してはならない。

制約。

- テストコードは実装しない。テストケースの設計までを担当する。
- UI、画面遷移、表示用状態管理を実装しない。
- 仕様を独断で変更しない。
- 物理層は DOM、ブラウザ API、描画 API に依存しない。
- 物理実装を担当するサブエージェントは、承認済みの `DESIGN.md` と `TESTCASES.md` を入力とし、テストケース作成時の未記録の推論や継続スレッドに依存しない。

### Reviewer

Reviewer は、高性能モデルで実行する独立レビュー役である。`read-only` 権限とし、コード、テスト、仕様、レビュー成果物を変更しない。

責務。

- 設計が上位仕様、既存アーキテクチャ、コーディング規約と矛盾しないか確認する。
- 数式、単位、境界条件、既知値、例外処理の妥当性を確認する。
- テストケースに正常系、性質、境界値、異常系が含まれるか確認する。
- 実装差分が承認済み設計とテストケースの範囲に収まるか確認する。
- UI テストケースに状態、エラー、キーボード操作、ラベル、ARIA、コントラストが含まれるか確認する。

Reviewer は、設計、テストケース、テストコード、実装差分をそれぞれ別のレビュー対象として扱う。物理レビューでは、実装者の説明を根拠にせず、記録された出典、既知値、単位、次元、性質、適用範囲から独立して検証する。

レビュー結果は、少なくとも次の項目を持つ構造化形式で返す。

```yaml
review_type: design | testcases | test-code | implementation
status: approved | changes-requested | needs-human
reviewed_files:
  - path: <path>
    hash: <content hash>
findings: []
conditions: []
rollback_to: design | testcases | test-code | implementation | none
```

`approved` だけを次工程への許可とする。従来の「条件付きOK」に相当する結果は、条件が解消され再確認されるまで `changes-requested` とする。修正が必要な場合は差し戻し先を明記し、情報不足で判断できない場合は、人間確認が必要な理由と選択肢を Coordinator に返す。

### DeliveryBuilder

DeliveryBuilder は、コスト重視モデルで実行する実装・検証エージェントである。

責務。

1. 環境構築、設定、定型的なプロジェクト配線を実装する。
2. 承認済みのテストケースをテストコードへ変換する。Reviewer のテストコードレビュー後に、想定した理由による Red を確認する。
3. 物理計算以外のロジックを実装する。
4. UI、スタイル、画面遷移、アクセシビリティを実装する。
5. テスト、型検査、lint、ビルドなどの決定的な検証を実行し、結果を報告する。

制約。

- 数式、単位、物理計算の期待値、テストケースの意図を独自に変更しない。
- Red 確認後のテストを削除、skip、期待値緩和、許容誤差拡大などで弱めない。変更が必要な場合はテストケース工程へ差し戻す。
- テストコード化に必要な情報が設計書やテストケースにない場合、推測で補わず Coordinator に停止を報告する。
- 物理計算ロジックの変更が必要になった場合、ArchitectPhysics への差し戻しを要求する。
- UI の仕様が曖昧な場合、実装を始めず人間の判断を求める。

## アーキテクチャ境界

各シミュレータは、少なくとも次の論理層を分ける。実際のディレクトリ名はアプリケーションのアーキテクチャで定める。

```text
core/                    共通の型、シミュレータ登録、ルーティング契約
simulators/<id>/domain/  物理モデルと純粋関数
simulators/<id>/app/     入力検証、状態管理、表示用データ変換
simulators/<id>/ui/      コンポーネント、スタイル、アクセシビリティ
simulators/<id>/scene/   描画と可視化
```

`domain/` は物理層であり、DOM、描画ライブラリ、UI 状態に依存しない。`app/` は domain の API を利用して UI 用の状態に変換する。`ui/` と `scene/` は domain の公開 API だけを利用する。

物理計算タスクと UI・統合タスクは別タスクにする。1タスクで両方を変更する必要がある場合は、先に物理 API を確定・実装し、その後に統合タスクを作成する。

## タスク成果物

タスクごとの永続的な情報は会話だけに置かず、ファイルに記録する。配置とテンプレートは実装時に確定するが、最低限以下を持つ。

```text
docs/simulators/<id>/
  SPEC.md                 シミュレータの要件と受け入れ基準
  DESIGN-OUTLINE.md       タスク間の公開 API と全体構成
  TASKS.md                タスク、依存関係、進捗（作成ルールは `docs/tasks-authoring-rules.md`）
  tasks/<task-id>/
    DESIGN.md             タスク設計
    TESTCASES.md          承認対象のテストケース
    REVIEW.md             Reviewer の判断と指摘
    EVIDENCE.md           baseline、Red、Green、最終検証の証跡
    DECISIONS.md          人間確認が必要だった事項と決定
```

真実の優先順位は次のとおりとする。

```text
SPEC.md > DESIGN-OUTLINE.md > DESIGN.md > TESTCASES.md > 実装
```

下位成果物が上位成果物と矛盾する場合、実装を続けず矛盾した上位の工程へ戻す。同じ事実を複数の成果物に複製せず、下位成果物は上位成果物を参照する。

レビュー承認は、`REVIEW.md` に記録された対象ファイルとハッシュに対してだけ有効とする。承認後に対象ファイル、上位成果物、または参照する公開 API が変更された場合、Coordinator は影響する承認を失効させ、タスク状態を `stale` に戻して再レビューする。`SPEC.md` または `DESIGN-OUTLINE.md` の変更時は、影響するタスク、テストケース、テストコード、実装を列挙してから再開する。

## 実行プロファイル

すべての変更へ同じ工程を強制せず、Coordinator がタスク開始時に次のプロファイルを確定する。プロファイルを分類できない場合や工程の省略がプロダクトの振る舞いへ影響する場合は、人間に確認する。

| プロファイル | 対象 | 必須工程 |
|---|---|---|
| `full` | 物理計算、公開 API、ユーザーに見える振る舞いの変更 | ②Pと③〜⑨R。UI 影響があれば⑩も実施 |
| `ui` | UI、操作、画面遷移、アクセシビリティ | ②Pと③〜⑨R、⑩ |
| `lightweight` | 文書、設定、定型配線など、振る舞いを変えない低リスク変更 | 変更方針、対象検証、差分レビュー、最終コミット。省略工程と理由を記録 |
| `emergency` | 人間が緊急対応と明示した修正 | 人間が承認した省略範囲、最低限の検証、事後補完タスクを記録 |

テストを追加しないタスクでは、テスト不要の理由と代替検証を Reviewer が承認する。単に小さい、急いでいる、またはテストコードを書きにくいことは省略理由にしない。

## 開発フロー

### シミュレータ単位の開始

1. 人間と Coordinator が要件と受け入れ基準を `SPEC.md` に確定する。
2. ArchitectPhysics が `DESIGN-OUTLINE.md` に、物理層、アプリケーション層、UI 層の契約を設計する。
3. Reviewer が全体設計をレビューする。重大な問題または未決定事項があれば人間確認へ戻す。
4. Coordinator が `TASKS.md` に小さなタスクと依存関係を記録する。

### タスク単位の反復

| 工程 | 主担当 | 実施内容 | 次の工程への条件 |
|---|---|---|---|
| ②P Preflight | Coordinator / DeliveryBuilder | 作業ツリーとステージ状態を記録し、既存テストの baseline Green を確認する | 既存失敗が今回の変更と区別され、`EVIDENCE.md` に記録されている |
| ③ 設計 | ArchitectPhysics | 新しいサブエージェントで `DESIGN.md` を作成する | 設計書が完成している |
| ④ 設計レビュー | Reviewer | 設計を独立レビューする | `status: approved`。Coordinator が設計成果物をステージし、コミット候補を人間に提示する |
| ⑤ テストケース作成 | ArchitectPhysics | 設計工程とは別の新しいサブエージェントで `TESTCASES.md` を作成する | 設計レビューが有効である |
| ⑥ テストケースレビュー | Reviewer | テストケースを独立レビューする | `status: approved` |
| ⑦ テストコード作成 | DeliveryBuilder | 承認済みテストケースをテストコードに変換する | テストケースレビューが有効である |
| ⑦R テストコードレビュー | Reviewer | テストコードが承認済みテストケースを過不足なく実装したか確認する | `status: approved` |
| ⑦V Red 確認 | DeliveryBuilder | 新規テストが想定したアサーションと理由で失敗することを確認する | 無関係な失敗がなく、失敗理由が `EVIDENCE.md` に記録されている。Coordinator がテスト成果物をステージし、コミット候補を人間に提示する |
| ⑧ 物理計算実装 | ArchitectPhysics | 設計・テスト作成とは別の新しいサブエージェントで、承認済み成果物に従い物理計算を実装する | テストケース・テストコードの意図を満たす |
| ⑧ 非物理・UI 実装 | DeliveryBuilder | ロジック、UI、統合を実装する | 設計と公開 API を満たす |
| ⑨ 自動検証 | DeliveryBuilder | 対象テスト、全テスト、型検査、lint、ビルドを実行する | Green であり、結果が `EVIDENCE.md` に記録されている |
| ⑨R 実装差分レビュー | Reviewer | 実装差分が承認済み設計とテストの範囲内か独立レビューする | `status: approved` |
| ⑩ 画面 UI の確認 | 人間 | UI に影響するタスクだけ、実ブラウザで受け入れ確認する | 人間が受け入れる |
| 完了ゲート | Coordinator | 成果物、承認ハッシュ、検証証跡、必要な人間確認を再確認する | 実装成果物をステージし、最終コミット候補を人間に提示する |

設計に問題が見つかった場合は③へ戻る。テストケースの問題は⑤へ、テストコードへの変換の問題は⑦へ、物理計算実装の問題は⑧の物理計算実装へ、非物理ロジックや UI の問題は⑧の DeliveryBuilder 担当へ戻る。上位成果物へ戻った時点で、変更の影響を受ける下位のレビュー承認、Red、Green、コミット候補を失効させる。仕様やデザインに関わる判断が必要なら、Coordinator が人間に確認する。

同一原因による修正は最大3回まで試みる。3回で解消しない場合、Coordinator は原因、試行内容、次の選択肢を `DECISIONS.md` に記録して人間に確認する。

## コミット手順

コミットの単位は、次の3種類とする。

1. ④の設計レビュー完了後の設計コミット
2. ⑦Rのテストコードレビューと⑦VのRed確認後のテストコミット
3. ⑨Rの実装差分レビュー完了後の実装コミット。UI に影響するタスクでは⑩の人間確認後、UI に影響しないタスクでは⑨R後に提示する

`lightweight` では最終コミットだけを作成する。`emergency` のコミット位置は人間が承認した計画に従う。Coordinator が以下を順番に実施する。

1. タスク開始時に記録した `git status`、既存のステージ済み差分、現在の差分を比較し、対象タスクに関係する変更だけを特定する。タスク開始前からステージ済み変更が存在する場合、今回のコミット候補を作成せず、人間が既存ステージを解消するまで停止する。
2. 対象ファイルにタスク外の変更が混在する場合はステージせず、人間へ対象差分と選択肢を提示する。ファイル単位で分離できる場合だけ次へ進む。
3. `git add -- <path>...` で対象ファイルだけをステージする。`git add .`、`git add -A`、既存ステージを変更する `git reset` は使わない。
4. ステージ済み変更が今回の候補だけであることを確認する。候補外のステージ済み変更を検出した場合はコミット候補を失効させ、人間に確認する。
5. 一意な Proposal ID を発行し、タスク ID、コミット種別、ステージ済みファイル、cached diff のハッシュ、コミットメッセージ、検証結果、会話セッションを一つの候補として記録する。同時に有効な候補は1件だけとする。
6. 人間へコミット候補を提示する。
7. 人間が同じ会話で「コミットしてください」と明示承認した場合だけ、最新の有効な Proposal ID を承認したものとして扱う。別セッションの承認や失効済み候補には適用しない。
8. 実行直前に、ステージ済みファイル、cached diff のハッシュ、コミットメッセージ、必要なレビュー承認が提示時から変わっていないことを再確認して `git commit` を実行する。
9. いずれかが変わった場合は承認を失効させ、コミットを実行せず、更新した候補をあらためて提示する。

コミット候補の一時状態は `.agent-state/commit-proposal.json` に保存し、Git 管理対象外とする。少なくとも Proposal ID、タスク ID、工程、会話セッション識別子、ステージ済みファイル、cached diff ハッシュ、メッセージ、作成時刻を持たせる。候補の失効またはコミット完了時に状態を無効化する。この状態ファイルは人間の承認そのものを代替せず、承認対象が変化していないことの検証だけに使う。

通知形式は次に固定する。

````markdown
## コミット候補

**工程**: ④ 設計レビュー完了 / ⑦R・⑦V テスト成果物完了 / ⑨R・必要なら⑩ 実装完了

**Proposal ID**: `<task-id>-<stage>-<unique-id>`

**ステージ済みファイル**:
- `path/to/file`

**コミットメッセージ案**:
```text
<type>(<scope>): <summary>
```

**検証結果**:
- <実行したコマンドと結果>

**ステージ差分ハッシュ**: `<hash>`

内容を確認し、実行する場合は「コミットしてください」と送信してください。
````

人間が修正を指示した、承認を保留した、または拒否した場合、Coordinator は `git commit` を実行しない。候補を失効させ、今回追加したステージだけを保持するか解除するか人間に確認する。既存のステージ済み変更は変更しない。

## テストと検証

テストケースは高性能モデルが設計し、テストコードはコスト重視モデルが実装する。これにより、物理的・仕様的な期待値の判断と、定型的なコード化を分離する。

Red / Green は次の条件で成立する。

1. タスク開始時に既存テストを実行し、baseline Green を確認する。既存失敗がある場合は、今回のタスクと区別して記録し、人間の許可なく無視しない。
2. ⑦R後、新規テストが承認済みテストケースに対応するアサーションで失敗することを確認する。構文エラー、型エラー、依存不足、環境不良だけの失敗は Red とみなさない。
3. Red 時に無関係なテストが新たに失敗していないことを確認する。
4. 実装後、同じテストを変更せずに Green にする。
5. Red 確認後にテストコードまたは上位成果物を変更した場合、テストコードレビューと Red 確認をやり直す。

物理計算では、既知値だけでなく、次を必要に応じてテストケースに含める。

- 保存則、単調性、対称性、可逆性などの性質
- 単位変換
- 最小値・最大値・臨界値の近傍
- 不正値、範囲外、NaN、Infinity に対する挙動
- 一次資料または信頼できる参照資料に基づく既知値と出典
- 実装経路とは独立した参照計算または高精度計算との比較
- 浮動小数点許容誤差の根拠
- 乱数を使う場合の固定 seed と再現性

UI では、状態遷移、エラー表示、キーボード操作、ラベル、ARIA、コントラスト、画面遷移をテストケースに含める。

Hooks は、エージェントによる判断を代替するためではなく、決定的に検証できる規約を強制するために使う。型検査・lint・テスト・層をまたぐ禁止 import は検証スクリプトと CI を正とし、Git 操作の保護など CI で代替できないものだけを Hook の候補にする。

| `scripts/verify-task-state.*` | 必須 | 承認対象ハッシュ、工程状態、Red / Green 証跡、コミット候補の整合性を検証 |
| `scripts/hash-files.*` | 必須 | Reviewer が対象ファイルの SHA-256 を生成する |
| コミット補助スクリプト | 必須 | Proposal の作成・承認状態・差分再検証と、承認済みコミットの実行 |
| `scripts/validate-agent-foundation.*` | 必須 | Agent、Skill、Hook、実行時状態の設定を機械検証 |
| `.codex/hooks.json` | 必須 | CI や lint で代替できない Git 操作の禁止・保護だけを初期導入 |

### スクリプト

`scripts/` はアプリケーションの機能を実装する場所ではなく、エージェントの工程、品質、Git 操作を機械的に検証する実行基盤である。各スクリプトの責務は次のとおりとする。

| ファイル | 概要 | 詳細 |
|---|---|---|
| `scripts/check-architecture.mjs` | アーキテクチャ境界の検査 | `src/optics/` と `src/simulators/*/domain/` を探索し、物理層から `ui`、`scene`、`app`、UI ライブラリ、ブラウザ API への依存を検出する。違反時は失敗する。 |
| `scripts/verify-fast.mjs` | タスク中の高速検証 | アーキテクチャ検査後、対象 workspace に定義された `lint`、`typecheck`、`test` を実行する。ビルドは実行しない。例: `node scripts/verify-fast.mjs --workspace apps/prism-sim` |
| `scripts/verify.mjs` | 最終・CI 用の完全検証 | アーキテクチャ検査後、全 workspace または指定 workspace の `lint`、`typecheck`、`test`、`build` を実行する。⑨および CI で使う。 |
| `scripts/verify-task-state.mjs` | タスク工程ゲートの検証 | `REVIEW.md` の承認状態と対象ファイルの SHA-256、必須成果物、`EVIDENCE.md` の baseline / Red / Green / 最終検証を確認する。UI 影響がある実装ゲートでは `ui_acceptance: accepted` を必須とする。 |
| `scripts/hash-files.mjs` | レビュー対象の固定 | 指定ファイルの SHA-256 を算出し、`REVIEW.md` に貼り付ける `reviewed_files` YAML を出力する。承認後の変更検出に使用する。 |
| `scripts/validate-agent-foundation.mjs` | 基盤設定の自己検証 | 必須 Skill、Agent 定義、Hook、検証スクリプト、`.agent-state/` の Git 除外を検証する。`npm run agent:validate` から実行する。 |
| `scripts/commit-proposal.mjs` | コミット候補の状態管理 | ステージ済みファイル一覧と cached diff の SHA-256 を `.agent-state/commit-proposal.json` に保存する。`create`、`status`、`approve`、`invalidate` を提供し、承認時に差分未変更を再確認する。このスクリプトはコミットを実行しない。 |
| `scripts/commit-approved.mjs` | 承認済みコミットの実行 | Proposal ID、承認状態、ステージ済みファイル、差分ハッシュを再確認し、一致時だけ `git commit` を実行する。成功後に commit hash を状態へ記録し、`git push` は実行しない。 |
| `scripts/lib/project.mjs` | 共通内部ライブラリ | Git ルート取得、引数解析、リポジトリ外パスの拒否、Node・npm workspace スクリプトの起動を共通化する。Windows では Node 経由で npm CLI を起動する。単独実行はしない。 |

主な呼び出し関係は、`verify-fast` / `verify` → `check-architecture` と `lib/project`、Reviewer → `hash-files`、Coordinator → `verify-task-state` と `commit-proposal`、人間の明示承認後 → `commit-approved` である。CI は `validate-agent-foundation` と `verify` を実行する。

### AGENTS.md

`AGENTS.md` には詳細な手順を複製せず、すべての作業で守る短いルールだけを置く。

- タスク開始時に確認する成果物と真実の優先順位
- タスク分類表に従い、既定の担当エージェントを選ぶこと
- 分類不能または例外の場合だけ人間に確認すること
- 実行プロファイルごとの工程ゲートと、成果物が承認済みであることの確認
- タスクの実行プロファイル、UI 影響の有無、レビュー対象ハッシュの確認
- 実装後に必要な `verify-fast` または `verify` の実行
- Git コミットは人間の明示承認後だけに実行すること

役割固有の詳細、チェックリスト、成果物テンプレートは `AGENTS.md` ではなくエージェント定義と Skill に置く。

### AGENTS.md と CLAUDE.md の配置

このワークスペースでは Codex と Claude Code を併用する。両者の指示ファイルは、同じシミュレータの実装ディレクトリに併存させる。

```text
AGENTS.md                           Codex のプロジェクト共通指示
apps/<simulator-id>/
  AGENTS.md                         Codex のシミュレータ固有指示
  CLAUDE.md                         Claude Code のシミュレータ固有指示
docs/simulators/<simulator-id>/
  SPEC.md                           両ツールが参照する仕様・受入基準
  DESIGN-OUTLINE.md                 両ツールが参照する全体設計
  TASKS.md                          両ツールが参照するタスク一覧
```

`AGENTS.md` は Codex に、`CLAUDE.md` は Claude Code に対する指示ファイルであり、ファイル名だけを機械的に置換した同一文書ではない。Codex 固有の役割分担、Skills、Hooks、コミットProposalの規約は `AGENTS.md` と本設計書に置く。Claude Code 固有の操作や設定は `CLAUDE.md` に置く。

物理計算、実装境界、テスト方針など両ツールで守る技術規約は、必要な範囲で両方の指示ファイルに同期し、仕様・受入基準・数式・タスク進捗は重複させず `docs/simulators/<simulator-id>/` の成果物を正とする。両方の指示が仕様と矛盾する場合は、`SPEC.md` を優先してから指示ファイルを更新する。通常のタスク実行で片方の指示ファイルを削除・移動・上書きしてはならない。

### Skills

Skills は、モデルの役割を決めるものではなく、反復する作業手順を一貫して実行するために使う。各 Skill の `description` には、起動条件と対象外を明記する。

| Skill | 起動する場面 | 主な利用者 | 内容 |
|---|---|---|---|
| `simulator-task-cycle` | 既存シミュレータのタスクを選択した実行プロファイルで進める時 | Coordinator | タスク分類、プロファイル選択、工程ゲート、成果物の生成順、差し戻し、停止・人間確認の手順 |
| `simulator-review` | 設計・テストケース・実装差分をレビューする時 | Reviewer | レビュー観点、重大度、差し戻し先、定型出力、成果物への記録方法 |
| `physics-validation` | 物理式、定数、近似、数値計算、物理的期待値を設計・レビューする時 | ArchitectPhysics、Reviewer | 出典、適用範囲、単位、次元、既知値、性質、独立参照計算、許容誤差、再現性の確認 |
| `simulator-scaffold` | 新しい物理シミュレータを追加する時 | Coordinator、ArchitectPhysics、DeliveryBuilder | `SPEC.md`、全体設計、タスク一覧、登録、画面、テストの雛形 |
| `ui-acceptance` | ⑩の人間による画面確認を準備する時 | DeliveryBuilder、Coordinator | UI の自動確認、手動確認チェックリスト、既知の制約、受け入れ結果の記録形式 |
| `commit-proposal` | ④、⑦V、または完了ゲートでコミット候補を作る時 | Coordinator | 既存変更との分離、Proposal ID、限定的なステージング、差分ハッシュ、メッセージ案、承認後の再確認とコミット |

`simulator-task-cycle` は、タスクを実装するたびに起動する中心 Skill とし、実行プロファイルごとの必須工程を管理する。`simulator-review` は Reviewer のみが使用し、実装コードを変更しない。`physics-validation` は物理的根拠を含む設計、テストケース、実装レビューで必ず併用する。`ui-acceptance` は人間の受け入れ判断を代替しない。

`commit-proposal` はコミットを自動実行しない。人間の「コミットしてください」という明示承認を受けて初めて、Coordinator にコミット実行を許可する。

`TASKS.md` のフェーズとタスクの粒度、必須項目、テンプレートは `docs/tasks-authoring-rules.md` に定義する。`simulator-task-cycle` と `simulator-scaffold` は、このルールを参照して `TASKS.md` を作成・更新する。

### 検証スクリプトと CI

機械的に判定できる品質は、エージェントの自己申告ではなくスクリプトと CI で検証する。

| 検証 | 実行タイミング | 実行主体 |
|---|---|---|
| 対象テスト、lint、型検査 | 実装・テストコード変更後 | DeliveryBuilder の `verify-fast` |
| 全テスト、lint、型検査、ビルド | ⑨、最終コミット候補、CI | DeliveryBuilder と CI の `verify` |
| domain 層の禁止依存 | `verify-fast` と CI | lint ルールまたは専用スクリプト |
| UI の自動確認 | ⑨と⑩の準備時 | DeliveryBuilder |
| 工程状態、承認ハッシュ、検証証跡 | 各レビュー後とコミット候補作成時 | Coordinator の `verify-task-state` |

`verify-fast` は短時間で終わる対象限定の検証にし、`verify` はリポジトリ全体の検証にする。物理計算の性質テスト、境界値、異常系は通常のテストスイートに含める。

工程ゲートは `verify-task-state` に `--task-dir`、`--gate`、`--profile`、`--ui-impact` を渡して検証する。`UI影響: あり` の実装ゲートは、`EVIDENCE.md` の `ui_acceptance: accepted` がなければ通過させない。

### Hooks

初期構成では、軽量で決定的な Git 保護 Hook だけを導入する。直接の `git commit`、`git push`、`git add .`、`git add -A`、破壊的な Git 操作を `PreToolUse` で拒否し、承認済みコミットは検証ラッパー経由で実行する。テストやビルドのような重い Hook は初期導入しない。

Hooks を追加するのは、次の条件を満たす場合だけとする。

- 判定が決定的で、AI の判断を必要としない。
- lint、テスト、CI、Codex の承認設定だけでは実現できない。
- 誤ってブロックしても回避手順が明確である。

導入候補は以下に限定する。

| Hook | 目的 | 導入条件 |
|---|---|---|
| `PreToolUse` の Git 保護 | 直接の `git commit`、`git push`、広範な add、破壊的操作を拒否する | 初期構成で導入。承認済みコミットは Proposal 検証ラッパーだけが実行する |
| `PreToolUse` のテスト凍結保護 | Red を確認後のテストを、再レビューなしで弱める変更を拒否する | タスク状態と凍結解除手順をファイルで機械判定できた場合 |
| `Stop` の簡易検証 | コード変更があるターン終了時に高速検証を要求する | 実行時間と対象変更を限定できた場合 |

Git 保護以外の Hook を導入する前に、同じ検証を `verify-fast` または CI で実行できる状態にする。Hook の信頼確認と更新管理も必要なため、初回の最小タスクを1周してから追加の必要性を判断する。

実装時には、プリズム分光シミュレータの最小タスク1件で全工程を1周し、成果物、権限、モデル割当、Skills、検証スクリプト、CI が期待どおり機能することを確認してから他タスクへ適用する。
